# Big Leaf Water Lab — 개발 셋업 계획

## Context

`big_leaf_water_generator_plan.md`에 기술 설계(폴더 구조, schema, Sprint 0~10, MVP 3개)는 정리됨. 그러나 **실제 개발을 시작하기 위한 메타-결정**(레포 셋업, 협업 워크플로우, GH 코드 관리, Claude harness, agent 분담 등)은 아직 미정.

이 계획은 그 메타 셋업을 정리한다. 목표: 한 시간 내에 첫 commit + 다음 며칠 내에 Phase A(인프라) 완료.

## 1. 개발 Phase (현재 결정 기준 재구성)

원 plan의 Sprint를 현재 단계 우선순위에 맞춰 재배치.

### Phase A — 인프라 (1주차)

- A.1 GitHub private repo 생성 + main branch protection
- A.2 Python project (uv + pyproject.toml + ruff + pytest)
- A.3 Typer CLI skeleton (`leaflab --help` 동작)
- A.4 Pydantic v2 schemas (candidate / params / metrics, `schema_version` 포함)
- A.5 Claude Code harness: `.claude/settings.json`, `.claude/CLAUDE.md`
- A.6 GitHub Actions CI (pytest + ruff)

검증: `uv run leaflab --help`, `uv run pytest`, CI 그린

### Phase B — Schema + GH Bridge (2주차)

- B.1 schema → `leaflab init-run <id>`, `leaflab validate <path>` 명령
- B.2 GH에 첫 generator (단순 3-leaf spine)
- B.3 GH → `params.json` + `leaf.stl` export 스크립트 (`gh/scripts/export_candidate.py`)
- B.4 `leaflab check-geometry` (trimesh 기반)

검증: `init-run cand_0001` → GH export → `check-geometry` 통과

### Phase C — Fast water proxy (3~4주차)

- C.1 `particle_drop.py` (water curtain 샘플링 + 낙하)
- C.2 `impact_angle.py` (raycast + normal_impact_score)
- C.3 sliding tangent flow + edge escape
- C.4 drain target + splash proxy
- C.5 `leaflab fast-sim runs/<id>` 명령

검증: 후보 한 개에 `fast_metrics.json` 생성, normal_impact_score < 0.25 필터 동작

### Phase D — Scoring + visual metrics (4~5주차)

- D.1 `compute_silhouette.py` (facade / eye-level / top-view)
- D.2 `score_water`, `score_visual`
- D.3 `leaflab score`, `leaflab rank` (Pareto)

검증: 후보 10개 생성 → `rank` 결과로 상위 3개 자동 추출

### Phase E — Karamba 구조 proxy (5~6주차)

- E.1 `KarambaSetup.gh` (shell mesh + brass props + support)
- E.2 `karamba_metrics.json` export (`gh/scripts/export_karamba_metrics.py`)
- E.3 `score_structure` 결합

검증: 후보별 mass / max_displacement / overturning_ratio 비교 가능

### Phase F+ (보류)

- F: OpenFOAM local contact case (WSL2 셋업 포함)
- G: ParaView postprocess
- H: Blender render bridge

Phase E 완료 후 우선순위 재검토.

## 6. Grasshopper 코드 변경 대응 (핵심 이슈)

### 문제 1 — `.gh` 파일 binary

`.gh`는 binary. diff/merge 불가능. 둘이 동시 수정하면 충돌.

### 문제 2 — Rhino 8 = CPython 3.9 고정 (중요)

Rhino 8 GH `Python 3 Script` 컴포넌트는 **임베디드 CPython 3.9** 사용. 우리 `uv venv` 아님. 만약 GH에서 `leaflab/`을 직접 import 하면:

- `leaflab/` 전체가 Python 3.9 문법으로 묶임 (`match`, `X | Y` 타입, `Self`, `TypeVarTuple` 등 사용 불가)
- pydantic v2 (3.9 지원하지만 일부 기능 제한)
- 의존성도 3.9 호환 필요

이는 받아들이기 어려운 제약. → **boundary 명확히 분리**.

### 전략 — GH-side는 thin IO shim만, `leaflab` import 금지

`gh/scripts/*.py`는 다음 역할만:

- GH에서 받은 mesh / dict / list → STL / JSON 파일로 serialize
- 또는 파일 → GH 객체 (deserialize, import_results.py)
- **`leaflab/` import 절대 금지**
- 의존성: stdlib + Rhino 8 기본 (`Rhino`, `Grasshopper`, `System`) + `# r: trimesh` 정도

`leaflab/`는 자유롭게 Python 3.11+ 문법 사용 가능. GH ↔ leaflab 사이는 항상 **JSON/STL 파일 경계**로 통신.

워크플로우:

```
GH (Rhino 8 CPython 3.9)               leaflab (uv venv, Python 3.11+)
─────────────────────────              ──────────────────────────────
LeafGenerator.gh
  ↓ (mesh + params dict)
gh/scripts/export_candidate.py
  ↓ writes
runs/cand_0001/params.json
runs/cand_0001/geometry/leaf.stl
                                        ↓ reads
                                        leaflab check-geometry
                                        leaflab fast-sim
                                        leaflab score
                                        ↓ writes
                                        runs/cand_0001/fast_metrics.json
                                        runs/cand_0001/score.json
GH `import_results.py`                  ↑ reads
  ↓ reads
runs/.../score.json
```

GH는 `leaflab` CLI를 호출하지 **않는다** (개발 중에는). 사용자가 GH export → 터미널에서 `leaflab` 명령 실행. Hops/subprocess 호출은 Phase D 이후 검토.

### `.gh` 충돌 방지

1. `.gh` 변경은 **단일 owner 원칙**: 한 번에 한 사람만 수정. 변경 전 Slack/메신저로 락 알림.
2. PR description에 GH 변경 요약: "added input port `landing_radius_m`", "renamed cluster X → Y"
3. 큰 구조 변경 시 `LeafGenerator_v2.gh` 새 파일로 두고 마이그레이션 후 v1 삭제.

### `gh/README.md` 필수 내용

- Rhino 8 CPython 3.9 제약 명시
- `gh/scripts/*.py`는 `leaflab` import 금지 (CI lint로 강제 가능)
- `# r: trimesh` 매직 주석 사용법
- 파일 경계 (JSON/STL) 통신 패턴 설명

## 7. 코드 / 스키마 진화 대응

- **schema versioning**: 모든 `params.json` / `metrics.json`은 `schema_version: "1.0"` 필드 필수
- **Discriminator 패턴** — `schema_version`을 `Literal["1.0"]`로 못 박으면 구버전 JSON 로드 시 즉시 reject되어 migrate 불가. 대신:
  1. raw JSON load → `schema_version` 필드 inspect
  2. version별 Pydantic 모델 dict로 dispatch (`MODELS = {"1.0": ParamsV1, "1.1": ParamsV2}`)
  3. 매칭 모델로 parse
  4. migrate 시 구버전 모델 → 변환 함수 → 신버전 모델
- **Pydantic v2 model_validator**로 마이그레이션 함수 작성
- `leaflab migrate runs/` 명령: 구버전 후보 → 새 버전 변환
- **Breaking schema change**:
  1. `schema/version.py`에 새 enum 값 추가
  2. 새 Pydantic 모델 작성 (구버전 보존, deprecate 주석)
  3. `migrate.py`에 변환 로직 추가
  4. PR 라벨 `schema-change`
  5. README에 마이그레이션 노트
- **알고리즘 변경**(예: scoring 가중치 수정): `metrics.json`에 `algorithm_version` 별도 필드. 비교 시 동일 버전끼리만.

- **Labels**: `phase-A`, `phase-B`, ..., `schema-change`, `gh-binary`, `bug`, `infra`, `in-progress`

### 매일

- 시작: `git fetch && git rebase origin/main` → `gh issue list --assignee @me --state open` → 리뷰 대기 PR 처리
- 종료: WIP 라도 push (브랜치는 본인 소유 명확히), 작업 중인 이슈에 짧은 진행 코멘트

### 주간 (15~30분 동기화)

- schema 변경 사항 공유
- 큰 디자인 결정 (PR description으로 부족한 것)
- `runs/` 후보 비교 (외부 스토리지 보면서)
- Milestone 진행률 확인

### PR 정책

- 작게 (한 Issue = 한 PR)
- PR description에 `Closes #<issue>` 명시
- 머지 전 `cavecrew-reviewer` 실행 → 발견 사항 처리 → 사람 리뷰 → 머지
- `schema-change` 라벨 PR은 둘 다 approve 필요
- `.gh` 수정 PR은 동시 수정 충돌 방지 위해 머지 즉시 (장기 보관 금지)

### Conflict 처리

- `.gh` 충돌: 일찍 머지한 쪽 우선, 늦은 쪽이 GH 열고 재작업
- `.py` 충돌: 표준 git merge
- schema 충돌: 둘 다 모여 토의 (15분)

## 15. 작업 추적 & 세션 운영 (확정 정책)

### 결정 사항

| 차원 | 도구 |
|---|---|
| **Phase 단위** | GitHub Milestone (`Phase A`, `Phase B`, ...) |
| **작업 단위** | GitHub Issue (label로 phase 묶음) |
| **세션 내 분해** | `TaskCreate` (in-session, 비영구) |
| **세션 시작 컨텍스트 복구** | **매번 plan mode 실행** |
| **큰 설계 결정 기록** | plan mode 출력 → `docs/plans/<date>-<topic>.md` (역사 기록만) |
| **영구 상태 문서** | **만들지 않음** (CLAUDE.md만 minimal, stale 방지) |

### 왜 이 조합인가

- **CLAUDE.md에 "현재 phase X"를 안 쓰는 이유**: 영구 stale 위험. phase 전환 깜빡하면 Claude가 잘못된 단계로 작동. 대신 매번 plan mode가 진실 확인 → 깨끗.
- **phase 문서를 안 만드는 이유**: 살아있는 문서는 PR마다 갱신 강제 안 하면 stale. 갱신 강제하면 오버헤드. GitHub Issues는 머지 시 자동 close → 갱신 자동.
- **plan mode를 매번 실행하는 이유**: context 손실 후에도 일관성. plan mode가 GH Issues 조회 + 현재 코드 상태 검토 → 이번 세션 plan 확정. Compact 이후에도 동일 protocol.
- **TaskCreate 사용 위치**: plan mode 종료 후 실제 작업 들어가면 plan을 5~10개 in-session task로 분해. 세션 끝나면 소멸 (다음 세션은 다시 plan).

### 세션 시작 protocol (Claude가 매번 수행)

```text
1. 사용자가 "start" 또는 "다음 task" 등으로 세션 시작
2. Claude: plan mode 진입 (자동 또는 사용자 트리거)
3. Claude: gh issue list --milestone "<current>" --state open 조회
4. Claude: git status, git log, runs/ 상태 확인
5. Claude: 이번 세션 plan 작성 (해당 plan 파일에)
6. 사용자 승인 → ExitPlanMode
7. Claude: TaskCreate로 plan을 in-session task로 분해
8. 작업 진행, TaskUpdate로 진행 추적
9. 세션 종료: PR open + 진행 코멘트 (해당 Issue에)
```

### plan 보관

- 큰 설계 결정 plan (이 문서 같은 것): `docs/plans/2026-05-21-setup.md`로 commit
- 일상 세션 plan: 임시 plan 파일 (`~/.claude/plans/`)에만 두고 git에 안 올림 (스팸 방지)
- 단, 중요한 설계 결정이 있으면 PR description에 plan 일부 인용
